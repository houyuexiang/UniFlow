## 3) 偏差清单

- **P1（新发现，影响现场）大小写绕过段节点保护**：`PUT /api/config {"path":"logging:loglevel","value":"Warning"}` 返回 200 且把 `Logging:LogLevel` 对象整体替换成标量（/tmp 副本实测，PROBE_AFTER 证据见上）。根因：`ConfigService.Navigate`（ConfigService.cs:420-429）`if (!cur.TryGetProperty(seg, out cur))` 在未命中时把 `cur` 置为 `default(JsonElement)`，随后的 `cur.EnumerateObject()` 抛 InvalidOperationException → 被 `ReadPath/ReadPaths` 的 catch 吞掉返回 null → `CheckNodeKind` 视为「新建，允许」。**大小写不敏感回退是永远走不到的死代码**。batch 端点更糟：`ReadPaths` 对任一小写失配 path 抛异常 → 整个结果为空 → 该批**所有**字段都失去当前值、保护全旁路。现有测试全部用精确大小写，故 300 全绿掩盖此问题。修复方向（给实施方，不代改）：Navigate 内用局部变量承接 TryGetProperty 的 out 值，未命中再对**原 cur** 做大小写不敏感匹配；并补小写 path 回归测试。严重度 P1 而非 P0 的理由：需管理鉴权、前端 FORM_FIELDS 均为精确大小写，正常 UI 不触发；但 API 直调/脚本一次即可损坏配置文件。
- **P2（声明数字不符）Playwright 用例数**：`grep -o "test("` 静态计数 = api.spec.js 19 + ui.spec.js 14 = **33**，与宣称的 43 不符（README 也无 43 出处）。可能为陈旧数字或包含非 test( 计法。
- **P2（设计取舍，已有文档与告警，可接受）**：send 失败时状态机保持 Ready → 下一轮对**同一条**重复下发 COMMENT（命令已投递、DB 未推进）。代码注释（L659-662）已明示、命令声明幂等、有 Error+degraded。建议后续加「本次已投递 barcode 内存标记」或 DB 写重试，避免依赖幂等。
- **P3（观察）**：`CheckNodeKind` 同时拦「对象→数组 / 数组→对象」异类节点（L36-37），无专项测试但行为合理；`Logging:LogLevel` 对象本体不可写（先过保护→再被 kind=string 类型校验拒，400），符合「只写叶子」设计。
